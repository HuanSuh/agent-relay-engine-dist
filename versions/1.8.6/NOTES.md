# agent-relay-engine 1.8.6 릴리스 노트

바뀐 범위: 1.8.5 → 1.8.6

### core

- **`process.restart` 의 덮인 사유.** 세션 프로세스(도는 턴이 쥐었거나 아직 얻지 않은)에 미뤄 둔 `restart()` 의 사유를 다른 사유가 덮으면 — 다른 `restart()` 가 그 사유를 바꾸거나(도는 턴이 없을 때 그 프로세스를 내리는 경우 포함), Claude 가 모델 변경(`model-changed`)으로, Codex 가 read-only 턴의 재기동(`tool-scope-*`)으로 그 프로세스를 내리면 — metric 은 여전히 내려간 프로세스 하나에 하나(`tags.reason` 은 내린 사유)이고, 덮인 처음 사유를 같은 metric 의 태그 `deferred` 로 남긴다(`{ reason: 'config-changed', deferred: 'watchdog' }`). 두 사유가 같으면 `deferred` 는 없다. 1.8.5 는 덮인 사유가 지표에서 사라져 `watchdog` 같은 이상 신호를 놓쳤다. 프롬프트·설정·정책 변경은 claude·codex 에서 표지가 붙은 프로세스를 그 비교 전에 표지 사유로 내리므로 `deferred` 가 붙지 않는다. 태그를 정확히 비교하는 metric 싱크·대시보드는 `deferred` 를 허용한다.
- **스스로 끝난 프로세스를 두고 부른 `restart()`.** 미뤄 둔 `restart()` 가 붙은 프로세스가 스스로 끝나거나 다른 길로 내려가는 중이라 그 사유로 이미 센 뒤, 그 프로세스를 두고 `restart()` 가 오면(그 프로세스를 쥔 턴·아직 프로세스를 얻지 않은 도는 턴을 끊거나 유휴 세션) 내려간 프로세스가 없어 세지 않는다. 턴은 1.8.5 처럼 다시 보내도 되는 `error` 로 끝나고 다음 턴은 새로 띄운다. 1.8.5 는 이번 사유로 한 번 더 셌다. 아직 아무 프로세스도 없을 때 도는 턴을 끊는 `restart()` 는 1.8.5 처럼 센다(도는 턴도 프로세스도 없으면 세지 않는다). 백엔드가 종료를 표기했지만(`exited`) 세션에서 빼지 않은 프로세스를 두고 부른 `restart()` 도 세지 않는다 — claude·codex 는 표기할 때 세션에서 빼므로 직접 만든 백엔드만 해당한다. 소비자가 할 일은 없다.
- **`resolveSession` 문맥의 `turnId`·`signal`.** `SessionResolveContext` 에 선택 칸 `turnId?`(그 설정을 쓰는 턴의 id — 턴 이벤트의 `turnId` 와 같다)와 `signal?: AbortSignal` 이 늘었다. `signal` 은 턴이 중지·강제 닫기·정리로 끝나거나 10초 상한을 넘기면 abort 하고 `signal.reason` 은 `'stopped'` 또는 `'timeout'` 이다. 훅이 값을 돌려준 뒤에는 abort 하지 않는다. 턴 안에서는 시작 전 대기 중에 `dispose()`·`evict()`·`stop({force})`·`TurnOptions.signal` 이 와도 바로 abort 하고, 훅을 기다리던 턴은 설정 오류가 아니라 끊긴 대로(`interrupted{signal}`·강제 재시작이면 그 오류) 닫힌다. 턴 밖 경로(Codex 분기 세션 열기·규칙 저장)는 `turnId` 가 없고, 분기는 `consult` 의 `signal` 이나 상한 초과로, 규칙 저장은 상한 초과로만 abort 한다. relay 의 백엔드 고르기에서 부르는 훅은 `turnId`·`signal` 이 없고 상한도 없다(기존 동작). 훅이 두 칸을 안 쓰면 바뀌는 것은 없다.
- **`backend-kit`(experimental).** 직접 백엔드를 만드는 쪽만 해당한다. `discardProc` 에 `reason` 을 주어 표지(`restartPending`)가 붙은 프로세스를 내리면 그 표지 사유가 태그 `deferred` 로 남는다. 타입·export 는 바뀌지 않았다.
- **`usage.costUsd` 는 그 턴의 비용이다(값의 뜻이 바뀐다).** `usage` 이벤트의 `costUsd` 는 백엔드가 세션 누계로 알려도 그 턴 하나의 비용이다. `SessionStatus.usage.costUsd`·세션 기록 `usage.costUsd` 는 턴 값의 합이고, `budget.perTurn.costUsd` 는 턴 값을, `budget.perSession.costUsd` 는 그 합을 본다. 1.8.5 의 Claude 는 CLI 세션 누계를 그대로 실어(같은 세션 두 턴이 `0.10`, `0.25`) 둘째 턴부터 턴 값이 과다했고, 세션 합은 누계를 다시 더해 더 과다했다. 1.8.6 은 같은 두 턴이 `0.10`, `0.15` 이고 세션 합은 `0.25` 다. `usage` 이벤트를 직접 더해 세션 비용을 구하던 소비자는 그대로 더하면 맞다. 마지막 `usage` 값을 세션 누계로 쓰던 소비자는 `engine.status(sid).usage.costUsd` 를 읽거나 이벤트 값을 더한다. 1.8.5 로 남은 세션 기록의 `usage.costUsd` 는 과다한 채로 남는다 — 세션 예산을 쓰면 그 세션의 기록을 고치거나 새 세션으로 시작한다. Codex 는 비용을 싣지 않아 바뀌지 않는다. 직접 만든 백엔드(`backend-kit`)도 `usage.costUsd` 를 그 턴의 값으로 낸다 — 엔진 골격은 받은 값을 그대로 세션 합에 더한다.
- **metric `cost.cumulative_regressed`.** `Metric` 유니언에 `{name:'cost.cumulative_regressed', value:1, tags:{accepted:'true'|'false'}}` 가 늘었다. 백엔드가 알린 세션 누계 비용이 직전 누계보다 줄었을 때 낸다(Claude). `accepted` 는 그 값을 새 누계·턴 값으로 받았는가다. `name` 으로 갈라 처리하는 metric 싱크는 모르는 이름을 허용한다. 이름을 `switch` 로 빠짐없이 가르던 코드(`never` 검사)는 한 갈래를 더한다.
- **`started.forked`.** `started` 에 선택 칸 `forked?: true` 가 늘었다. 분기 세션(`fork`·`consult`)의 첫 턴 — 새 백엔드 세션이지만 원본 대화를 이어받아 시작한 턴 — 에만 싣는다. `resumed` 의 뜻은 그대로다(Claude 분기의 첫 턴은 `resumed:false`, Codex 는 `fork()` 가 연 스레드를 이어 쓰므로 `resumed:true`). 진짜 새 대화와 분기의 시작을 가르려면 `resumed:false` 와 `forked` 를 함께 본다. 모르는 칸을 버리는 소비자는 할 일이 없다. relay 는 그대로 넘긴다.

### claude

- **CLI 누계 비용을 턴 값으로.** CLI `result` 의 `total_cost_usd` 는 CLI 세션 누계다. 엔진은 직전 누계와의 차이를 `usage.costUsd` 로 낸다. 직전 누계는 세션 기록 `ext.claude.cliCostUsd` 에 남아 `--resume`·엔진 재기동 뒤에도 이어진다. 분기 세션은 원본의 마지막 누계(첫 턴이 복사할 때의 값)에서 시작한다 — CLI 의 분기 세션은 원본 누계를 물려받는다. 정상 종료한 프로세스 뒤의 `--resume` 은 누계가 이어지지만, 강제 종료(SIGKILL·크래시) 뒤 `--resume` 하면 CLI 누계가 그 호출 값부터 다시 센다 — 되돌아간 누계가 직전 누계보다 작으면 그 턴은 그 값을 턴 값으로 세고 다음 턴부터 다시 차이다. 되돌아간 누계가 직전 누계 이상이면(직전 누계가 작았고 그 호출이 비쌌으면) 되돌아간 것을 알 수 없어 차이만 세므로 그 턴은 적게 잡힐 수 있다. 곧 누계가 줄어든 `result` 는 이 세션의 현재 프로세스가 대화를 돌린 것이면(`--resume` 여부와 상관없이) 그 값을 턴 값·새 기준으로 받는다(metric `cost.cumulative_regressed{accepted:'true'}`). 일찍 실패한 `result`(오류이고 모델 턴 0)·교체된(이 세션의 현재가 아닌) 프로세스의 늦은 `result` 는 기준을 내리지 않고 턴 값 0 이다(`accepted:'false'`) — 다음 정상 턴이 누계 전체를 턴 값으로 내지 않게. 1.8.6 으로 처음 이어 가는 1.8.5 세션은 기록에 직전 누계가 없어 첫 턴이 누계 전체를 턴 값으로 낸다(한 번). 그런 세션을 분기한 세션의 첫 턴도 같다. 중지 뒤 늦게 온 `result` 처럼 받을 턴이 없거나 턴이 소비하지 않고 닫힌(중지·시간 상한 등) `result` 의 비용은 `usage` 이벤트 없이 세션 합(`SessionStatus.usage.costUsd`)에만 더한다 — `budget.perSession.costUsd` 가 실제 지출을 놓치지 않게. 그래서 세션 합이 `usage` 이벤트 값의 합보다 클 수 있다. 이 늦은 비용은 `budget.perTurn.costUsd` 판정에는 쓰이지 않는다. CLI 가 분기를 따르지 않은 프로세스의 `result` 는 원본 대화의 누계라 분기 세션의 누계·합에 넣지 않고, 그 턴의 `usage`·`perTurn` 판정에도 비용을 싣지 않는다. `ext.claude` 를 직접 읽는 소비자는 새 칸 `cliCostUsd` 를 허용한다.
- **`started.forked`.** 분기 세션의 첫 턴(`--fork-session` 으로 띄운 프로세스에서 처음 init 을 본 턴)에 싣는다. 그 첫 턴이 init 전에 끝나 다음 턴이 다시 분기하면 그 턴에 싣는다. init 을 본 뒤 보장 검사(내장 도구·MCP strict·범위·인증)로 `started` 없이 닫힌 첫 턴이면 분기는 이미 이뤄졌으므로 다음 턴은 `resumed:true` 이고 `forked` 는 어느 턴에도 오지 않는다. 곧 `forked` 는 한 분기 세션에서 최대 한 번이며 오지 않을 수 있다.

### codex

- **`started.forked`.** `fork()`·`consult` 가 `thread/fork` 로 연 스레드에 처음 보내는 턴에 싣는다(그 프로세스가 먼저 내려가 `thread/resume` 으로 이어 쓴 경우 포함). 그 스레드를 잃고 새 스레드로 열었으면 싣지 않는다.
